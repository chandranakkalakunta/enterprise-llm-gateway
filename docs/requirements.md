# Requirements

## Goals

- Act as the single entry point for all LLM-related work in the enterprise (commercial LLMs, customer-hosted/open-source LLMs, and internal RAG).
- Enforce corporate policy while giving controlled flexibility to power users.
- Protect corporate data with strong input controls.
- Provide useful, privacy-respecting usage visibility.
- Deliver a fast, unobtrusive user experience.

## Non-Goals

- Multi-tenant public SaaS version for individual developers.
- Replacing the enterprise’s internal RAG engine or vector database.
- Full prompt management / versioning platform.
- Fine-grained content moderation beyond policy-driven guardrails.

## Functional Requirements

### Must Have (P0)

- [ ] **F1**: Single entry point for all LLM traffic (commercial + internal/open-source + internal RAG).
- [ ] **F2**: Policy-driven routing based on content/purpose, user type (Normal vs Super AI User), user preferences (within limits), and RBAC roles.
- [ ] **F3**: Corporate administrators can define purpose → allowed model(s) mappings.
- [ ] **F4**: Strong, policy-driven input guardrails / DLP that prevent sensitive data from leaving the trust boundary unless explicitly allowed.
- [ ] **F5**: Normal AI Users follow corporate policy. Super AI Users can override within clearly defined limits.
- [ ] **F6**: UI shows available models. Models the user is not eligible for are greyed out / disabled.
- [ ] **F7**: Full end-to-end streaming support.
- [ ] **F8**: Semantic cache for repeated or similar queries.
- [ ] **F9**: Privacy-respecting usage metering and analytics.
- [ ] **F10**: Users can rate responses 1–5 stars. Low ratings (especially 1-star) are recorded as strong negative signals.
- [ ] **F11**: Internal knowledge queries can be routed to the enterprise RAG engine.
- [ ] **F12**: Horizontal scalability to support the full user base of a large enterprise.
- [ ] **F13**: Token limits, rate limits, and model eligibility for commercial LLMs are the same for UI and API access (based on identity + purpose + role).
- [ ] **F14**: Prefer using a small number of enterprise-grade API keys per commercial provider (managed by the Gateway). The Gateway itself enforces per-user / per-team quotas and isolation.
- [ ] **F15**: Strict data isolation — no user can ever see another user’s prompts, responses, or detailed activity.
- [ ] **F16**: Conversation memory / multi-turn context must be managed per-user (and per-conversation) with strict isolation. No mixing of contexts between users.
- [ ] **F17**: AI Agents are treated as first-class consumers of the Gateway (alongside human users and internal applications).
- [ ] **F18**: The UI shall display available models grouped by Parent model, showing all applicable sub-models/variants. Models the user is not eligible for shall be greyed out or disabled.
- [ ] **F19**: Every response shall clearly indicate which model generated it (e.g. “Response generated by: Claude 4 Sonnet via Enterprise LLM Gateway”).

### Should Have (P1)

- [ ] **F20**: Automatic fallback / circuit-breaking when a model is unavailable or rate-limited.
- [ ] **F21**: Quota and rate limiting per user, team, department, or purpose.
- [ ] **F22**: Basic output filtering / response guardrails.
- [ ] **F23**: Integration with corporate Identity Provider (SSO).
- [ ] **F24**: Configurable retention and redaction policies for logs and analytics.

### Could Have (P2)

- [ ] **F25**: Advanced semantic routing.
- [ ] **F26**: A/B testing or shadow traffic for new models.
- [ ] **F27**: Cost-aware or carbon-aware routing preferences.

## Analytics & Logging Requirements

- Per-user token consumption (without storing raw prompt/response content by default).
- Token consumption by category / purpose (code, research, finance, etc.).
- Per-department (or cost-centre) token consumption.
- Aggregated reports that help the enterprise understand usage patterns and cost drivers.
- 1–5 star feedback linked to request metadata (privacy-preserving).

**Open decision:** Whether to store token consumption at the individual request level or only in aggregated form.

## Non-Functional Requirements

| Category           | Requirement                                                                                                                      | Priority |
|--------------------|----------------------------------------------------------------------------------------------------------------------------------|----------|
| Performance        | Typical added latency well under 30 ms. Users must not feel the gateway. Full streaming support.                                 | P0       |
| Scalability        | Support all users of a large enterprise.                                                                                         | P0       |
| Security & Privacy | Strong input guardrails + strict isolation between users.                                                                        | P0       |
| Deployment         | Must support fully private deployment (customer VPC / on-prem). Cloud-hosted private instance is acceptable.                     | P0       |
| High Availability  | No single point of failure for core routing path.                                                                                | P1       |
| Observability      | Metrics, logs, and traces for operators without leaking sensitive content.                                                       | P0       |
| Usability          | Clear model visibility and simple feedback mechanism.                                                                            | P0       |

## Constraints & Assumptions

- Users accept that conversation history is managed by the Gateway with strict per-user isolation.
- Enterprise prefers using a small number of high-limit commercial API keys rather than per-user keys.
- Internal RAG and privately hosted models are available and can be registered with the Gateway.
- Consumer Pro/Max subscriptions (Claude Pro, SuperGrok, Gemini Advanced, etc.) do not automatically provide API access. Separate API accounts and billing are required.
